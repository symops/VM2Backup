# VM2Backup

Backup of virtual machines (VMware ESXi / vCenter, or a folder of VMs) to a folder, a network folder (SMB), FTP, FTP over TLS or SCP, with a
a Windows service for scheduled tasks, an HTTPS web interface that does all the work, and a small Windows control panel (`VM2Backup.exe`).
Native Win32 C++17; TLS and cryptography by OpenSSL, linked statically (libraries are fetched and built by `tools/deps.sh`, see `docs/DEV.md`); x64 and x86 builds; 16 interface languages besides English.
Author: Symo <symops@gmail.com>.

## The program is a control panel

**The work is done in the web interface at https://127.0.0.1:8443/ (default login `admin` / `admin`)**: servers, tasks, schedule, backups,
restore, history and settings. `VM2Backup.exe` is only a small fixed-size control panel: the state of the service (running / stopped /
not installed), its version and data folder, the state of the web site, the buttons Start / Stop / Restart service, Open web interface,
Open logs folder, the language and Exit. It talks to the service over the named pipe and needs administrator rights (service control).
Command line: `/pipe <name>`, `/selftest [ms]`, `/guitest <file>` (tests). The full former Windows GUI (views, wizards, dialogs, tests) is kept
for a possible restore in `/home/symo/Claude/.wip/gui-full-backup/` (sources, language files, tests, build and test scripts of the time before the panel).

## What it does

* **Sources:** VMware ESXi 6.x – 9.x and vCenter (vSphere API). **Cold backup by default:** a running VM is shut down (VMware Tools), held for the whole copy (lock on vCenter, a marker in the VM on every host; it stays off through pauses and lost connections until the copy is done or cancelled), read in place without a snapshot and started again afterwards; the downtime is in the history. **Hot backup** (checkbox, with a warning) keeps the VM running: snapshot, copy of the frozen disks, snapshot removed afterwards. See `docs/ESXI.md`. Or a folder where every sub-folder is a VM.
* **Targets:** local folder, **network folder (SMB / CIFS, UNC path with its own user and password)**, FTP, FTPS / FTPES (TLS), SCP
  (SSH by libssh2; SFTP is not supported). The service cannot see the drive letters of a user: use the UNC path. A folder with VMs may also lie on a network share.

* **Archive:** tar split into independent volumes, compressed with xz (LZMA2, the only compressor: levels 0-9 = the real xz presets `xz -0` .. `xz -9`, default 7, a task without a level takes the one of the Settings, see `docs/WEB.md` "Compression levels"; archives are `*.tar.xz[.enc]`; the number of compression threads is a setting, Auto by default), optionally encrypted
  (AES-256-GCM, PBKDF2), every volume with a SHA-256 in the manifest.
* **Resume:** a backup, a verification and a restore continue after a lost connection (volume by volume) and after a restart of
  the service. Restore to ESXi uploads whole files (HTTP PUT cannot append): a lost connection re-sends the current file.
* **Restore:** to a folder, or to an ESXi host / vCenter (files are uploaded and the VM is registered); both from the web site's Backup Explorer ("Restore to": Folder / ESXi host or vCenter, with the same choices as the old Windows dialog; admin role only, because the service writes as SYSTEM / connects with stored credentials).
* **Lock-out protection:** a domain account is locked after a few wrong passwords, and one call to a server with a wrong password counts twice (Kerberos, then NTLM; measured on a real
  domain controller). So when a server (SMB, FTP, SCP, ESXi / vCenter, a VM folder on a share) refuses the credentials (wrong / locked / disabled / expired password, logon not allowed;
  never a network error or a timeout), the service remembers it in `state.json` and does **not contact that server again** from a scheduled run or from another element of the same task:
  the element ends `Failed` with the mark "skipped" and the text "The credentials of server ... were rejected on ...; not tried again until the server record is changed or "Try again" is pressed".
  Changing the login data of the record (user, password, address, port, key) lifts the block by itself; so does "Try again" on the Datacenter page (`servers.unblock`, admin) and a successful
  connection. A manual run and "Test connection" make exactly one attempt and update the mark. Other servers are not affected. Details: `docs/WEB.md`.
* **Scheduler:** every N minutes/hours/days, weekly, monthly, once; time windows with a speed limit per window; bandwidth limit.
* **Web site (on by default, localhost only):** HTTPS, users with roles (admin / operator / viewer), TOTP 2FA, listening interfaces
  chosen by the administrator. A fresh installation has the user `admin` with the password `admin`; the site listens on localhost only
  by default; whoever can reach the site with that password controls the service (and the machine, as SYSTEM) - change it under Users,
  and keep the site on localhost or change the password before choosing a network address. The site administers itself (addresses, port, certificate, users, 2FA with a QR code, audit log), offers 17 languages, the network drive / network browse and folder pickers and the HTML report of a history entry; `VM2BackupService.exe /reset-web` is the way back in when nobody can sign in. See `docs/WEB.md`.

## Build and test (Linux, clang + MinGW-w64, Wine)

    tools/deps.sh build all     # once: OpenSSL (and the other libraries of deps/deps.lock) for x64 and x86
    ./build.sh                  # build/x64/ ; ARCH=x86 ./build.sh -> build/x86/ ; ONLY=autotest|service|gui
    ./package.sh                # dist/VM2Backup-Setup.exe (picks the 64- or 32-bit installer)
    tools/run-tests.sh [--seed N] [--skip a,b] [--only a,b]
                                # native (ASan/UBSan), core (x64 + x86), ftp, ssh, esxi, web, gui, package
    tools/run-winvm.sh x86      # the whole plan on a REAL Windows VM (x86 / w10 / w11), deleted afterwards: docs/WINDOWS-TESTS.md
    python3 tools/gen_lang.py --update   # after adding TR("...") strings; --check, --missing <code>

Details for developers: `docs/DEV.md`; tests on real Windows: `docs/WINDOWS-TESTS.md`; ESXi/vCenter: `docs/ESXI.md`; web site: `docs/WEB.md`; installation: `docs/INSTALL.en.txt`.

## What is verified, and what is not

* The bulk of the tests runs under **Wine** and against local test servers (OpenSSH `sshd`, paramiko, pyftpdlib, own mock servers).
* **Real Windows** (`tools/run-winvm.sh`, `docs/WINDOWS-TESTS.md`): the whole plan ran on real VMs of **Windows 10 x86 22H2**, **Windows 10 x64 22H2 (Russian)** and
  **Windows 11 25H2 (Russian)**, each deleted after its run: installer (silent install, update in place over a running service, removal, reinstall), the service under the
  real Service Control Manager (delayed auto start, STOP_PENDING, crash recovery), the named pipe ACL (Administrators + SYSTEM only), the panel at 100 / 125 / 150 % scaling,
  the web site with Windows' own TLS clients (TLS 1.2 everywhere, TLS 1.3 negotiated on Windows 11), DPAPI over a service and a Windows restart, the native autotests, FTP / SCP
  against servers on the Linux host, and **real SMB** (`WNetAddConnection2W` against a Samba share with a user and a password, also an SMB 3 encrypted share on Windows 11:
  backup / verify / restore, wrong password, unreachable server, a server that stops and returns in the middle of a backup, network browse, `net use` drives).
  The Windows 11 SmartScreen warns about the Setup.exe that carries the Mark of the Web; the release can be **code-signed** (`tools/sign.sh`, optional step of `package.sh` via `VM2B_SIGN_PFX`, see `docs/SIGNING.md`). Round 7 (Windows 11 25H2, a self-signed TEST certificate): `Get-AuthenticodeSignature` = UnknownError / Valid (root trusted) / HashMismatch (changed after signing); SmartScreen still shows its window for the signed file, but names the publisher; UAC shows "Verified publisher" for the signed installer and "Unknown publisher" for the unsigned, untrusted and tampered files; Smart App Control switched to On through the Windows Security UI (not through the registry) blocked some files (a tampered signed one, a freshly built unsigned exe) but not others, and the signed VM2Backup service runs with SAC = On. **A test certificate gives no SmartScreen reputation**: the real effect on users can only be checked with a real OV / EV certificate (`docs/SIGNING.md`). A **real Active Directory domain** (two Windows Server 2022 VMs, `tools/run-winvm.sh domain`) covered: Kerberos / NTLM accounts, the service as LocalSystem / a domain user / a gMSA (real password rotation after a synchronized clock shift, no restart needed), expired / locked / disabled / must-change passwords with the lock-out guard, the network root listing the domain's servers (DsGetDcName + LDAP), unattended logon after every restart. Not covered on Windows: real ESXi / vCenter (the ESXi group ran on the x86 VM only against the emulators, 5 tests limited by the Windows SMB client cache; a real ESXi 7 was tested separately under Wine, see below). **Round 8 (Windows 10 x86, third cycle, 30.10.2026):** the **signed installer on Windows 10** (`Get-AuthenticodeSignature` NotSigned / UnknownError / Valid / HashMismatch, silent install and update in place of the signed package by the 32-bit launcher, signed binaries in Program Files, the Windows 10 "Windows protected your PC" and "Open File - Security Warning" windows with the publisher shown); the **schedule across daylight saving transitions on the real Windows clock and C runtime** (W. Europe, Pacific, Lord Howe, GMT; three bugs found and fixed: a non-existent local minute ran an hour EARLY, a repeated minute was never met by the scheduler, and a running service ignored a time-zone change; a damaged installer now explains itself in `%TEMP%\VM2Backup-Setup.log`); **no handle / GDI / USER / memory leak** of the service and the panel in 36 minutes of load (816 panel opens, 136 backups, 2 service restarts); NTFS cases (EFS file refused with a clear message, compressed and sparse files, a 255-character name, 5000 files, EICAR under a running Defender, a file that vanishes during the copy: all end with a clear file error or a bit-exact restore, never with a silent success); `ftp_large_streamed` 10 of 10 on the guest. **Round 9 (Windows 10 x64 22H2, Russian, third cycle, 31.10.2026):** the whole plan from scratch with one command (install 25 min, plan 6 h), the same checks on x64 + Russian UI (the SmartScreen / UAC windows of the signed installer read in Russian with the publisher named; the schedule across DST transitions in W. Europe / Pacific / Lord Howe and winreal in four Russian zones; no leaks in 36 minutes; NTFS / Defender cases); no product defect found, harness defects fixed: the SCP lock-out guard tests no longer read the sshd log through the SMB client cache (now over TCP, deterministic), `scp_fault_drop_listing` always cuts inside the listing, the FTP upload timeout was a hang of the test FTP server (pyftpdlib spins after an unclean TLS close; guarded) and the client now waits for its TLS close_notify to be written.
* **ESXi / vCenter** (backup and restore) was tested against the mock servers in `tools/testservers/esxi_mock.py` (profiles 6.0 ... 9.0, host and vCenter) and, since 01.11.2026,
  against a **real VMware ESXi 7.0 U3n (build 21930508)** running nested under KVM (`tools/esxi7/`, group `esxireal`, `docs/ESXI.md` "Проверка на настоящем ESXi 7"):
  login / list / wrong credentials, backup of a powered-off VM through a snapshot over the datastore HTTP interface in four encryption / compression modes, verify, resume after a pause, restore to a folder and
  restore to the host itself (the restored VM registers and powers on), all through the engine and through the service; the sha256 of every restored disk is bit-identical to the one taken on the host before the backup.
  The real run found and fixed two defects (the SOAPAction version decided the property set: `config.keyId` was refused; a duplicate root folder in the restore dialog) and one limit that is NOT fixed:
  **a powered-on VM is backed up from a clone** (the datastore HTTP interface answers HTTP 500 for the disks a running VM holds, also for the base disk a snapshot froze; the host clones the frozen disks itself through `VirtualDiskManager.CopyVirtualDisk_Task`, the clone is read over `/folder` with `Range` and deleted afterwards): proven on the real ESXi 7.0.3 in four compression / password / volume modes (sha256 of the restored disk equal to the one taken before the snapshot), restore to a folder and to the host, pause / power-off / power-on / resume inside the disk / cancel, a running VM with its own snapshot tree (consolidated into one disk, earlier snapshots not copied, said in a warning). **Guest writes during the copy are proven on the real host too** (Alpine Linux guest with a raw block writer on a second disk, serial log to a file, host-side timeline watcher): in 2 modes (xz 1; password + xz 5 + ~100 MB volumes) and a pause / resume run, the copy took 4-11 minutes while the guest wrote 3,000-11,000 more blocks after the snapshot; the restored disk is exactly the state of the guest's last write before the snapshot (65,535 blocks checked, 0 violations, no write made after the snapshot), a restored VM boots and confirms its disk itself, and the detector is shown to catch splices, flipped bits, lost writes and a single write from the future. The copy is crash-consistent (no VMware Tools in the test guest, so quiesce was not tested). SSH and NFC were evaluated and not needed (`ExportSnapshot` is NotSupported on a standalone ESXi 7.0.3).
  **A paused copy survives a power cycle of the VM** (02.11.2026): the resume fingerprint covers only the frozen state (snapshot, disks), the VM's live configuration files (`.vmx` / `.vmxf` / `.nvram` / `.vmsd`, which ESXi rewrites when the VM is powered off or on) are read once at the start and kept in the resume state, so a paused copy continues by the same snapshot and the same volumes after one or several power-off / power-on cycles and also when the VM is off at the time of the continuation (the clone of the frozen state is read); a destroyed or re-created snapshot or changed frozen data starts the copy over with a warning. Proven on the mock (`esxi_resume_survives_power_cycles`, 8 cases, fails on the old code) and on the real ESXi 7.0.3 with the guest writing (`docs/ESXI.md` "Возобновление копии"). The option `snapshot.history` (default on, checkbox on the task page) switches the copy of the VM's other snapshots off (their memory, side branches, the list): proven on the mock and on the real ESXi 7 (a VM with a snapshot tree restores and powers on either way; the disks the current state depends on are always copied). A **real vCenter Server 7.0.3** (VCSA under qemu in its own VM, the ESXi host added to it; recipe in `docs/ESXI.md` "vCenter 7.0.3 на настоящем VCSA", `tools/esxi7/vcsa.sh`) passes the same real-host tests (group `vcreal`, 6 of 6: list, wrong credentials / lock-out guard, backup of off and running VMs through vCenter, verify, restore to folder and to vCenter with sha256 equal to the reference, service flow, restore options). **Cold backup (default, 03.11.2026)** on the real ESXi 7.0.3 with an Alpine guest that runs open-vm-tools: the guest is shut down through VMware Tools, the VM is marked as held (`extraConfig vm2backup.hold` + a note in the annotation), the disks are read in place without a snapshot or clone, a pause keeps the VM off and held, the continuation finished the same copy (sha256 of the disk in the backup = sha256 taken on the host with the VM off), the VM was powered on again (downtime in the history), `esxi.unlock_vm` and the next run (orphan marker) give a running VM back (powered on again); an explicit cancel and the other final endings are proven on the emulator and, for the off-VM variant, on the real host, a VM without Tools is refused with a clear text (and powered off only with the "force" option), a VM powered on behind the product's back makes the continuation start over. **A standalone ESXi 7.0.3 cannot lock a VM**: `DisableMethods` / `EnableMethods` / `QueryDisabledMethods` answer NotSupported and `root` cannot be denied access, so there the hold is a marker, not a lock (said in the log, in the history record and under the checkbox); the lock itself (vCenter) is proven on the emulator only, not on a real vCenter. See `docs/ESXI.md`, "Холодный (по умолчанию) и горячий бэкап". Not covered: several hosts / datacenters / clusters on a real vCenter, ESXi 6.x / 8 / 9 (still mock only; 9.0 details are assumed), encrypted VMs, vSAN, NFS datastores, VMware Tools quiesce.
* No incremental backups, no e-mail reports, no Hyper-V.
