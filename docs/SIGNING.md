# Подпись установщика VM2Backup (Authenticode)

Установщик `VM2Backup-Setup.exe` и все программы внутри него (`VM2Backup.exe`, `VM2BackupService.exe`, `VM2Backup-Setup.exe` для x64 и x86)
можно подписать цифровой подписью Authenticode. Подпись даёт пользователю:

* в запросе UAC строку «Проверенный издатель: <ваше имя>» вместо красного «Неизвестный издатель»;
* меньше предупреждений Microsoft Defender SmartScreen («Система Windows защитила ваш компьютер») для файла, скачанного из интернета;
* возможность запуска там, где включён Smart App Control (SAC): он блокирует неподписанные программы без репутации и не оставляет кнопки «выполнить в любом случае»;
* защиту от подмены: после любого изменения файла подпись становится недействительной.

Результаты проверок на Windows 11 25H2 с тестовым сертификатом записаны в `docs/WINDOWS-TESTS.md` (раздел «Раунд 7»). Коротко:

* подписанный установщик показывает в UAC «Проверенный издатель», а в окне SmartScreen называет издателя (если сертификат доверен на этом компьютере);
* неподписанный, подписанный недоверенным центром и изменённый после подписи файлы показываются как «Неизвестный издатель» (изменённая подпись Windows файл сама не блокирует);
* **окно SmartScreen для нового файла остаётся**, пока у файла / издателя нет репутации: тестовый сертификат её не даёт, только настоящий (EV сразу, OV по мере накопления);
* Smart App Control включается только через интерфейс «Безопасность Windows» (не записью в реестр); его решения по неподписанному коду зависят от облачной репутации и не детерминированы;
  служба VM2Backup, подписанная тестовым центром, при включённом SAC запускается.

## 1. Какой сертификат получить

Нужен сертификат **подписи кода** (Code Signing, EKU `1.3.6.1.5.5.7.3.3`) от коммерческого удостоверяющего центра, которому доверяет Windows
(DigiCert, Sectigo, GlobalSign, SSL.com, Certum и другие; в России, если нужен корень Минцифры, выбирайте по требованиям заказчика).
Закрытый ключ по правилам CA/Browser Forum должен храниться на аппаратном носителе (токен USB, смарт-карта) или в облачном HSM; обычный PFX-файл
с ключом новым покупателям уже не выдают (исключение: самостоятельная выгрузка из облачной службы подписи).

| Вид | Что проверяют | SmartScreen | Примечание |
|---|---|---|---|
| **OV** (Organization Validation) | существование организации, телефон, адрес | репутация накапливается: сначала предупреждение, пока файл не скачали достаточно людей без жалоб (обычно недели; репутация привязана к сертификату и к хэшу файла) | дешевле; при смене сертификата репутация теряется |
| **EV** (Extended Validation) | то же плюс усиленная проверка юридического лица | **немедленная репутация**: предупреждения SmartScreen для нового файла нет с первого дня (с 2024 года это правило ослаблено для новых сертификатов, но EV по-прежнему сильнейший сигнал доверия) | токен или облачный HSM обязательны; дороже |
| Облачная подпись (Azure Trusted Signing / Artifact Signing, DigiCert KeyLocker, SSL.com eSigner, Google Cloud KMS + CA) | как OV / EV, но ключ в облаке | как у выбранного вида | удобна для CI: ключ не выходит из HSM; подпись делается по API |

Почему EV даёт репутацию сразу: SmartScreen считает репутацию по цепочке «издатель, чей сертификат EV» как заведомо проверенную организацию,
поэтому подписанный им новый файл не попадает в категорию «нераспознанное приложение». Для OV репутации нет, пока облако Microsoft не увидит файл
у достаточного числа пользователей; до этого окно SmartScreen показывается, но с названием издателя вместо «Неизвестный издатель», и кнопка «Выполнить в любом случае»
остаётся доступной через «Подробнее».

Smart App Control доверяет программам, подписанным сертификатами из списка доверенных центров Microsoft (Microsoft Trusted Root Program и список
подписывающих служб), либо имеющим хорошую репутацию в облаке. **Свой самоподписанный корень, добавленный в «Доверенные корневые центры», SAC не признаёт** (см. результаты проверки).
Для SAC нужен именно настоящий сертификат от центра из программы Microsoft.

## 2. Как подписывать

Инструмент: `tools/sign.sh` (osslsigncode; на Linux хватает пакета `osslsigncode`).

```sh
# PFX; пароль в файле (права 0600), не в командной строке
tools/sign.sh --pfx cert.pfx --password-file cert.pass --name VM2Backup --url https://example.org/vm2backup \
              --timestamp http://timestamp.digicert.com --verify файл.exe [ещё.exe ...]

# пара PEM (ключ без пароля или с паролем в файле)
tools/sign.sh --cert chain.pem --key key.pem --password-file key.pass файл.exe

# пароль из переменной окружения / со стандартного ввода
VM2B_SIGN_PASSWORD=... tools/sign.sh --pfx cert.pfx файл.exe
printf '%s\n' "$PASS" | tools/sign.sh --pfx cert.pfx --password-stdin файл.exe
```

Пароль не попадает в командную строку и журнал: `sign.sh` переписывает его во временный файл с правами 0600 в каталоге с правами 0700 и удаляет по выходу.
Алгоритм хэша всегда SHA-256 (`-h sha256`). **Метку времени (`--timestamp`, служба RFC 3161) в настоящем выпуске указывайте всегда**:
без неё подпись перестаёт считаться действительной, когда истекает срок сертификата; с меткой остаётся действительной навсегда.
В тестах метка не используется (сети не нужно).

### Подпись при сборке пакета

`./package.sh` подписывает пакет, если задана переменная `VM2B_SIGN_PFX`:

```sh
export VM2B_SIGN_PFX=/путь/cert.pfx
export VM2B_SIGN_PASSWORD_FILE=/путь/cert.pass      # либо VM2B_SIGN_PASSWORD (не рекомендуется: остаётся в окружении)
export VM2B_SIGN_TIMESTAMP=http://timestamp.digicert.com
export VM2B_SIGN_URL=https://example.org/vm2backup  # необязательно
export VM2B_SIGN_CA=/путь/root.pem                  # необязательно: корень для проверки в конце подписи (без него «verification: failed» - ожидаемо)
./package.sh
```

Порядок: сначала подписываются все `exe` полезной нагрузки (`x64\*.exe`, `x86\*.exe` и загрузчик в `dist/VM2Backup/`), затем они упаковываются в cab,
и **последним** подписывается итоговый одиночный `dist/VM2Backup-Setup.exe` целиком (подпись закрывает и cab). Поэтому `VM2Backup.exe`,
`VM2BackupService.exe` и копия установщика в `Program Files\VM2Backup\` тоже подписаны, а UAC при запуске внутреннего установщика показывает издателя.
Без переменных пакет собирается как раньше, без подписи.

Устройство одиночного файла при подписи: цепочка «загрузчик + выравнивание до 8 байт + cab + хвост `VM2BPKG1` + размер», таблица сертификатов Authenticode
добавляется **после** хвоста. Загрузчик читает заголовок PE, находит начало таблицы сертификатов и ищет хвост перед ней. Выравнивание нужно, чтобы
подписывающий инструмент не добавлял нули между хвостом и таблицей (загрузчик допускает до 7 таких байт). Любые изменения подписанного файла (даже один байт) ломают подпись.

### Аппаратный токен и облачный HSM

`osslsigncode` умеет PKCS#11 (`-pkcs11module`, `-pkcs11cert`, `-key pkcs11:...`), для облачных служб используйте их программу подписи
(Azure: `Invoke-TrustedSigning` / dlib для SignTool; DigiCert KeyLocker: `smctl`). Требование к порядку то же: сначала exe внутри, потом итоговый одиночный файл.
Для SignTool из Windows: `signtool sign /fd sha256 /tr <URL метки> /td sha256 /a файл.exe`.

## 3. Как проверить

На Windows (PowerShell):

```powershell
Get-AuthenticodeSignature .\VM2Backup-Setup.exe | Format-List Status, StatusMessage, SignerCertificate, TimeStamperCertificate
# Status = Valid: подпись верна и сертификат доверен
# UnknownError / NotTrusted: подпись математически верна, но корень не доверен (так выглядит тестовый сертификат)
# HashMismatch: файл изменён после подписи
```

```bat
signtool verify /pa /v VM2Backup-Setup.exe
```

На Linux: `osslsigncode verify -in файл.exe -CAfile root.pem` (результат: `Signature verification: ok`). Вместе со сборкой: `tools/sign.sh --verify --ca root.pem`.
Проверка того, что подписаны и внутренние файлы: установите пакет и выполните `Get-AuthenticodeSignature "$env:ProgramFiles\VM2Backup\*.exe"`.

В свойствах файла (вкладка «Цифровые подписи») видны имя подписавшего и метка времени. Строки «Издатель» в UAC берутся из сертификата:
сведения о версии (`VM2Backup-Setup.rc`: CompanyName = «Symo», ProductName = «VM2Backup») показываются в окне SmartScreen и в «Свойствах», но «Проверенный издатель» в UAC — это Subject сертификата.

## 4. Тестовый сертификат (только для проверки механики)

`tools/make-test-cert.sh` создаёт на хосте корень `VM2Backup TEST Root CA` и сертификат `Symo TEST Code Signing` (RSA 3072, SHA-256, EKU подписи кода)
в `.winvm/shared/pki/` (каталог, PFX, пароль и ключи в `.gitignore`; в репозиторий не попадают). Такой сертификат:

* даёт `Get-AuthenticodeSignature` Status = `UnknownError` (корень не доверен) или `Valid` (после добавления корня в `LocalMachine\Root`);
* **не даёт репутации SmartScreen** и не принимается Smart App Control;
* годится для проверки порядка подписи, чтения подписанного одиночного файла загрузчиком и отображения издателя в UAC.

Реальная проверка поведения SmartScreen / SAC для пользователей возможна только с настоящим сертификатом и настоящими скачиваниями.
